# Role-Level AI Intelligence

An enterprise application that analyses the future AI impact of jobs. For 24 representative
**Finance-industry roles**, it derives:

`Role → Processes → Activities → Current Skills → AI Exposure → Activities Automated →
Activities Augmented → New Responsibilities → Future Skills → Future Role Profile`

It supports natural comparisons ("Compare Finance Analyst vs Procurement Analyst"), rankings
("Which 5 roles change the most?"), and — critically — **every conclusion is explainable**:
each activity's automation/augmentation score comes with a plain-English reason.

---

## 1. Quick start

```bash
cd enterprise-ai-role-intelligence
./run.sh
```

This creates a virtualenv, installs dependencies, seeds a SQLite database with 24 roles, and
starts the server. Open **http://localhost:8000** in a browser.

Manual equivalent:
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --reload --port 8000
```

Interactive API docs (auto-generated by FastAPI): **http://localhost:8000/docs**

Run tests:
```bash
python3 -m pytest tests/ -v
```

### Optional: enable LLM narrative generation
The app works fully offline with zero API keys (deterministic template narratives). To enable
richer, free-text narrative answers via Claude:
```bash
export ANTHROPIC_API_KEY=sk-ant-...
```
See `backend/llm.py` — this is the only place an LLM is called, and only for narrative text,
never for the underlying automation/augmentation numbers (see Architecture Decision #2 below).

## 3. How the AI/analytics layer actually works

**Key design decision:** the automation/augmentation *numbers* are produced by a **deterministic,
rule-based engine** (`backend/scoring.py`), not a black-box ML model. Each activity is tagged with
six attributes (`structured`, `repetitive`, `rule_based`, `requires_judgment`,
`requires_creativity`, `interpersonal`). Each attribute contributes a fixed number of points to an
automation score and/or an augmentation score, and every point is logged as a human-readable
**reason code** ("`'Invoice data entry' is structured, and is high-frequency and repetitive, and
follows explicit, codifiable rules -> 95% automation potential.`").

This directly satisfies the brief's requirement that **"the candidate must explain how the system
derived its conclusions"** — you can point to the exact rule that produced any number, which a
black-box classifier could not do without a separate explainability layer (SHAP/LIME).

A role's overall automation/augmentation % is the time-weighted average of its activities'
scores. A `confidence` rating (`high`/`medium`/`low`) is derived from how many activities were
assessed and how clearly automation vs. augmentation dominates.

Optionally, `backend/llm.py` can call the Claude API for free-text narrative questions (e.g. "why
are these 5 roles most exposed?") — but it is *only* used for prose generation on top of the
already-computed structured data, never to invent the percentages themselves. If no API key is
set, it falls back to a deterministic summary — this is the "external AI service unavailable"
fallback strategy the brief asks about.

### Extending it
- **Add roles/industries**: edit `data/generate_seed.py`, re-run `python3 data/generate_seed.py`,
  then `python3 -m backend.seed_loader` (or delete `role_intelligence.db` and restart the server).
- **New attribute / weight**: edit `AUTOMATION_WEIGHTS` / `AUGMENTATION_WEIGHTS` in
  `backend/scoring.py`.
- **Swap in a real NLP parser**: today `role → activities` mapping is curated data; a production
  version would add an NLP layer (e.g. spaCy/embeddings) to parse raw job descriptions into the
  same structured `activity` records the scorer already consumes — the scorer itself doesn't need
  to change.

## 4. API reference

| Endpoint | Purpose |
|---|---|
| `GET /api/roles?level=&search=` | List all roles with automation/augmentation summary |
| `GET /api/roles/{id}` | Full role profile: activities, reason codes, future profile |
| `GET /api/compare?role_a=X&role_b=Y` | Side-by-side comparison + narrative |
| `GET /api/rank?n=5` | Top-N roles by total AI exposure + narrative |
| `GET /api/health` | Liveness check |

## 5. How this maps to the interview questions in your document

The original brief also lists a set of interview-style questions. Here's how this codebase
answers each, concretely:

- **Source code organisation** → the `frontend/ backend/ data/ tests/` split above; inside
  `backend/`, routers/models/schemas/scoring are separated by concern.
- **Testing before demonstrating** → `tests/test_scoring.py` (unit tests on the engine) and
  `tests/test_api.py` (integration tests hitting every endpoint), runnable via `pytest`.
- **Deployment** → containerize with a `Dockerfile` (see below) behind Kubernetes/Cloud Run;
  CI runs `pytest`, builds the image, pushes to a registry, deploys.
- **Reducing unnecessary LLM calls** → structured scores never call an LLM at all (see §3);
  narrative generation is the only optional LLM call, and results could additionally be cached
  by `(role_a, role_b)` or `(n,)` key.
- **Handling external AI service unavailability** → `backend/llm.py`'s `_fallback_narrative()`.
- **Explainability & trust** → `reason` field on every activity, `reason_codes` list per role,
  `confidence` rating.
- **Scaling to 100,000 records** → swap SQLite for PostgreSQL (already abstracted via
  `DATABASE_URL` in `backend/config.py`), add pagination to `/api/roles`, and move the seed step
  to a batch ETL job instead of app-startup.

### Minimal Dockerfile (add if you want to containerize)

## 6. What to say if asked "why these architectural choices?"

1. **Rule-based scoring engine, not a trained ML model** — for a v1 with no historical
   ground-truth labels of "which tasks actually got automated," a transparent rule engine is more
   trustworthy and immediately explainable than a model that would need to be trusted on faith.
   It's also the "AI vs traditional logic boundary" decision called out in the brief: this is
   deterministic logic, not AI, by design.
2. **LLM used only for narrative, never for scoring** — keeps the trustworthy numbers
   deterministic and reproducible, and only spends LLM cost on the part that genuinely benefits
   from free-text generation.
3. **SQLite → PostgreSQL swap-in-place** — `DATABASE_URL` is the only thing that changes;
   SQLAlchemy models don't care which database is behind them.
4. **Config-driven roles** — new roles/industries are data (`roles_seed.json`), not code changes,
   matching the brief's "new functionality = add a service/config, not redesign the system."
